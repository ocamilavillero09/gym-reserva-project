Preparación del entorno

Haz esto una sola vez antes de empezar. Todos los casos asumen este punto de partida.

Desde la raíz del proyecto. Deja los tres servicios corriendo durante toda la sesión de pruebas.

3. Comandos para preparar y restaurar datos

Varios casos necesitan un estado que no se puede producir desde la interfaz, como dejar un bloque sin cupos. Se preparan con estos comandos contra MongoDB. 

# Dejar el bloque 1 sin cupos (Esc23, Esc29)
docker compose exec database mongosh gym_udem --eval \
  'db.slots.updateOne({slotId:1},{$set:{available:0}})'

# Dejar el bloque 1 con un solo cupo (Esc22)
docker compose exec database mongosh gym_udem --eval \
  'db.slots.updateOne({slotId:1},{$set:{available:1}})'

# Penalizar una cuenta por siete días (Esc27)
docker compose exec database mongosh gym_udem --eval \
  'db.users.updateOne({email:"ana.gomez@soyudemedellin.edu.co"},
   {$set:{estado:"PENALIZADO",penalizado_hasta:new Date(Date.now()+7*86400000)}})'

# RESTAURAR el punto de partida entre escenarios
docker compose exec database mongosh gym_udem --eval \
  'db.slots.updateMany({},{$set:{available:20}});
   db.reservations.deleteMany({});
   db.waitlist.deleteMany({});
   db.users.updateMany({},{$set:{estado:"ACTIVO",cancel_count:0,no_show_count:0,penalizado_hasta:null}})'

Ejecuta el comando de restauración antes de cada escenario. Si no, los contadores de cancelaciones que deja un escenario alteran el resultado del siguiente.

Antes de empezar a ejecutar

  • Restaura los datos entre escenarios. Es el error más fácil de cometer: los contadores de cancelaciones que deja un escenario alteran el resultado del siguiente y te dan fallos que no son reales.
  • Dos escenarios son acumulativos y no se restauran por dentro: Esc28 (los tres casos van seguidos hasta llegar a cinco cancelaciones) y Esc29 (los cuatro casos dependen del estado que deja el anterior).
  • Captura la evidencia en el momento. Varios resultados se pierden al recargar o al ejecutar el caso siguiente, sobre todo los avisos en pantalla, que desaparecen a los pocos segundos.
  • CP-004 es el único que no se automatiza y requiere una persona ajena al proyecto. Agéndalo aparte: no lo puedes hacer solo frente al computador.
  • CP-010 debe ejecutarse a mano contra MongoDB real. La prueba automatizada equivalente usa una base simulada que corre en secuencia, así que valida la lógica pero no la concurrencia.
